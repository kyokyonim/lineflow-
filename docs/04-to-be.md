# 04. To-Be 프로세스

```
[신청자] 신청서 입력 (신규 / 연장 / 해지)
   ↓
① 사전 Validation  (Collect-All: 모든 오류를 한 번에 반환)
   · 필수값, 형식, 요금제 허용, 단말 유형 호환성
   · 신규: 번호 직접 입력 불가, 이미 사용 중인 번호 차단
   · 연장: 번호 유지 → 통보서 첨부 확인 / 번호 변경 → 변경 필드가 실제로 달라졌는지 확인
   ├ 오류 → 코드 + 해결 방법 표시, 결재 진입 차단
   └ 통과
   ↓
[전자결재] 신청자 팀장 → 운영 팀장  (사람 승인 2단계)  ※ 3→2단계는 "제안"
   ↓
② 개통 직전 자동 비교  (결재 데이터 ↔ LegacyProv 데이터, 운영 담당자 눈 비교 대체)
   ├ FAIL → 원인 코드와 함께 신청자 통보
   └ PASS
   ↓
③ 처리
   ├ 신규 / 해지 / 연장(번호 유지) → 처리
   └ 연장(번호 변경) → 변경이 필요한 항목만 순차 실행 (단계별 상태 기록)
   ↓
④ 개통 직후 결과 검증  (배정 번호 풀, 요금제가 단말 유형과 맞는가)
   ├ 알려진 코드 → 조건부 자동 롤백 (후순위)
   ├ UNKNOWN → 운영 담당자에게 에스컬레이션 (사유 포함)
   └ 정상 → 이력 자동 기록 (엑셀 대장 대체) + 신청자 통지
```

## 정책
| 규칙 | 내용 | 비고 |
|---|---|---|
| R1 | 연장 기간은 최대 3개월 | |
| R2 | 번호 변경이 기본, 번호 유지는 예외 | 근거 미확인 (설정 값으로 둔다) |
| R3 | 번호 유지 시 통보서 첨부 필수 (존재만 확인) | 내용 검증은 개선 제안 |
| R4 | 번호 변경 시 사용 종료일도 함께 변경 | |
| R5 | LegacyProv 제약: 변경은 한 번에 한 항목씩 | 시스템이 순차 실행 |
| R6 | 신청 유형별 입력 가능 필드가 다르다 | 신규는 번호 직접 입력 불가, 연장은 기존 회선 필수 |
| R7 | 한 신청의 오류는 전체 반려 (일부 접수 없음) | 승인 단위가 신청 전체이므로 |

## 에스컬레이션 패키지 (운영 담당자에게 넘길 정보)
1. 어떤 신청인가 (신청 ID, 유형, 신청자, 핵심 값)
2. 어디까지 진행됐나 (이미 된 것과 안 된 것)
3. 어떤 오류가 났나 (우리 시스템의 확인 내용 + LegacyProv 원본 메시지)

## 개선 제안 (현행 정책 변경이 필요하므로 권한자 결정 사항)
- 승인 라인 3단계 → 2단계 (운영 담당자의 눈 비교 단계를 자동 비교로 대체, 병행 운영 후 전환)
- 통보서를 첨부파일 대신 구조화된 폼으로 입력
