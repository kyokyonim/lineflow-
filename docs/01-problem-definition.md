# 01. 문제 정의

## 한 문장 정의
회선 신청·연장·해지 업무에서 사람이 눈으로 하던 검증과 반복 입력을 규칙 기반 Validation, 자동 비교, 구조화된 Error Code로 대체하고, 해결할 수 없는 예외만 운영 담당자에게 넘기는 업무 자동화 시스템.

## 핵심 문제
**두 시스템에 같은 데이터가 존재하고, 그 둘이 같은지 확인하는 일을 사람이 한다.**

| 근본 원인 | 파생되는 증상 |
|---|---|
| 데이터가 세 곳에 분산 (ApprovalHub, LegacyProv, 엑셀 현황 대장) | 수동 비교, 연장 시 수작업 템플릿 |
| 오류 표현 체계 부재 (모호한 메시지, 자유 텍스트 비고) | 원인 추적 지연, 오류 집계 불가 |
| 규칙이 사람 머릿속에 있음 | 업무 지식의 속인화, 반복 문의 |

## 사용자
| 사용자 | 역할 | 핵심 니즈 |
|---|---|---|
| 신청자 | 회선 신청·연장·해지 | 한 번에 통과, 실패 시 이유와 해결법 |
| 신청자 팀장 | 1차 승인 | 승인할 내용을 한눈에 |
| 운영 팀장 | 최종 승인 | 규정에 맞는 건만 승인 |
| 운영 담당자 | 개통 처리, 예외 처리 | 반복 검증에서 벗어나 예외에 집중 |
| 시스템 관리자/개발자 (2차) | 규칙·Error Code 관리 | 배포 없이 규칙 데이터 변경 |

## 프로젝트 가치
- 오류 1건당 비용(재작업)이 큰 업무에서, **오류를 가장 싼 시점(신청 시점)에 차단**
- 자유 텍스트 기록을 Error Code로 구조화하여 **개선 우선순위를 데이터로 결정**
- 신청자의 대기 시간(리드타임)을 핵심 지표로 삼음
  (불편을 느끼는 사람은 신청자인데 개선을 요구할 사람은 운영 측이라는 구조적 특성)

## 설계 원칙: AI 적용 기준
- 입력과 정답이 **결정적**이면 규칙 기반(코드)으로 해결한다.
- 표현이 모호하고 문서가 방대한 영역(자연어 문의, 매뉴얼 검색)에만 AI(RAG)를 검토한다.
- 정책에 없는 판단(예: 소명서 내용의 타당성)을 시스템이 몰래 수행하지 않는다.
